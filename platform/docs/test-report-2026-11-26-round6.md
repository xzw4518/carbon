## 三、发现的缺陷

### P1-1　500 响应泄露数据库结构与 SQL 语句

**复现**：管理员登录，`POST /api/products`，`name` 传 300 个字符。

```bash
curl -X POST /api/products -d '{"name":"长...（300字）","code":"X","type":"一般产品","cls":"工业产品","unit":"吨"}'
```

**实际**：HTTP 500，响应体 `body.detail` 为：

```
### Error updating database. Cause: Data truncation: Data too long for column 'name' at row 1
### The error may exist in com/carbonbal/product/ProductMapper.java
### SQL: INSERT INTO product (org_id, name, code, type, cls, unit, ...) VALUES (...)
```

**影响**：任何登录用户输入超长字符串即可获得表名、列名、Mapper 类路径与完整 SQL，属于信息泄露，可被用于构造后续攻击；同时用户看到"服务内部错误"，无法得知是哪个字段超长。

**根因**：`GlobalExceptionHandler.handleOther` 把 `e.getMessage()` 直接放进响应；且字段长度无 `@Size` 校验，直接由数据库抛 `DataTruncation`。

**修复**：
1. `handleOther` 不再返回异常 message，统一为"服务内部错误，请联系管理员"；
2. 新增 `DataIntegrityViolationException` 处理，按原因分类返回：唯一冲突 → 409 `DUPLICATE`、超长 → 400「输入内容超出字段长度限制」、越界 → 400「数值超出允许范围」，且只取最内层原因，SQL 只进日志；
3. `ProductReq` / `AssetReq` 补 `@Size`、`@Pattern`、`@DecimalMin`、`@Min`/`@Max`；
4. 前端表单默认 `maxlength`（输入框 120、文本域 500）。

**验证**：同样请求返回 `400 {"detail":{"name":"名称最长 120 字"},"message":"参数校验失败"}`，响应体无 SQL。

### P1-2　已提交 / 已复核的核算期仍可补录读数，审批链失效

**复现**：把 2026-11 期间推进到 `submitted`，再新增一条读数：

```bash
POST /api/device-readings  {"deviceId":1,"ts":"2026-11-18T10:00:00","qty":1.5,...}
```

**实际**：HTTP 200，数据落库，期间状态仍为 `submitted`。

**影响**：报告已提交（甚至已复核、已批准）后仍能改底层数据，审批结论对应的数据与库中数据不再一致；审计上"已提交 v3"与"当前数据"对不上，合规审计无法通过。这是本轮最严重的数据一致性缺陷。

**根因**：`PeriodGuard.assertEditable` 只拦截 `status='locked'`，`submitted` / `reviewed` / `approved` 均放行。

**修复**：`PeriodGuard` 改为三档：
- `submitted` / `reviewed`：**写入前自动把期间回退到 `calculated`**，清空提交/复核痕迹，写 `rollback` 审计，提示用户需重新提交；
- `approved` / `locked`：直接 409 拒绝，提示"已批准/已锁定，如需更正请先解锁或重新开启核算"；
- `draft` / `calculated`：正常放行。

**理由**：直接全拒会让"提交后发现错误"无路可走（系统没有撤回接口）；全放行会让审批链失真。自动回退兼顾数据一致性与可用性，且回退动作可审计。

**验证**：`submitted` 写入 → 200 且状态变 `calculated`；`reviewed` 写入 → 200 且回退；`approved` 写入 → 409。

### P1-3　平台租户列表被测试残留污染

**复现**：连续执行几次 `mvn test` 与 `functional-cases.py`，用平台超管打开"平台概览"。

**实际**：`租户总数 10、活跃 10、账号 19`，租户列表 9 行为 `TST 功能测试租户 6xxxxx`，其中 8 个是零成员空壳租户（管理员账号已被后续用例删掉）。

**影响**：客户打开平台概览首先看到 9 个测试租户与虚高的账号数，直接影响交付印象；空壳租户无法删除（平台无删除接口），只能改库；`org` 表无限增长。

**根因**：
1. 6 个测试类（`TenantIsolationTest`、`SessionTenantTest`、`PlatformDomainTest`、`RoleApiTest`、`DetailApiTest`、`AuditApiTest`）都会新建租户，但没有清理；
2. `functional-cases.py` 建租户后同样不删；
3. 平台侧没有删除租户接口，残留只能靠脚本。

**修复**：
1. `ApiTestSupport` 增加 `@AfterAll cleanupTestTenants()`：删除 `org_id <> 1` 的角色页面、角色、成员、产品、设备、资产、租户，以及无租户归属的测试账号（保留平台超管）；
2. `functional-cases.py` 的 `cleanup()` 末尾按本次标记调用 `purge-test-data.sh --marker <suffix> --apply`；
3. 存量清理：删除 9 个 TST 租户、13 个测试账号、128 条软删产品、36 份软删报告、35 个测试设施（清理前已 `mysqldump` 备份到 `backend/backup/before-cleanup-20261126-162914.sql`）。

**验证**：跑完整套 `mvn test` 后 `org=1 / app_user=6 / user_tenant=5`，无新增残留；平台概览 `租户 1、账号 6、成员 5`。

### P2-1　批准人可以是编制人（职责分离缺口）

**复现**：`filler` 提交 → `reviewer` 复核 → `filler` 批准。

**实际**：HTTP 200，期间变为 `approved`。

**影响**：提交人自己批准自己提交的报告，中间那次复核形同虚设；现有校验只覆盖"复核≠编制""批准≠复核"，缺"批准≠编制"，四眼原则不完整，ISO 14064 内控审查会判为缺陷。

**修复**：`AccountingService.approve` 增加 `approver != submittedBy` 校验，返回 `409 SOD_VIOLATION`「批准人不能是编制人（职责分离）」。

**验证**：同流程返回 409 并被拒。

---

### P2-2　软删后无法复用编码/名称

**复现**：新建产品 `REUSE-001` → 删除 → 再用 `REUSE-001` 新建。

**实际**：
- 产品：`409 DUPLICATE`「产品编码已存在」，但列表里看不到该编码（已软删）；
- 设备、碳资产：**500**（撞唯一索引后未预检）。

**影响**：用户删错想重建、或编码规划复用时会卡死，提示信息还自相矛盾（说存在但看不见）；设备/资产直接 500，体验更差。

**根因**：唯一索引不含 `disabled`（`uk_product_code(org_id,code)`、`uk_device_code`、`uk_asset_name_year`），软删记录仍占用原值。

**修复**：新增 `UniqueKeys.release(value, id, maxLen)`，删除时把唯一字段改为 `原名#记录id`（按列长截断），释放原值并保留审计可追溯；已接入产品、设备、碳资产三处删除。

**验证**：产品删除后同编码重建 → 200；设备删除后同编码重建 → 200。

**未覆盖**：`supplier(name,product)`、`energy_mgmt(at_date)`、`tenant_role(name)` 属同类风险，`energy_mgmt` 的唯一键是日期无法改名，需单独设计，见"剩余风险"。

### P2-3　超长/超范围字段直接 500

与 P1-1 同源但表现不同：不带 SQL 泄露的路径也会 500。数值传 30 位整数（超出 `decimal(10,4)`）、名称 300 字，均返回 500 `INTERNAL`。

**修复**：`DataIntegrityViolationException` 兜底 + DTO 注解（见 P1-1）。

### P2-4　枚举字段不做校验

**复现**：`POST /api/products`，`type` 传"不存在的类型"，`unit` 传"光年"。

**实际**：200，脏数据落库并出现在列表筛选里。

**修复**：`ProductReq.type` / `cls` 加 `@Pattern`，单位加 `@Size(16)`。

**验证**：返回 `400 {"detail":{"type":"产品类型只能是 一般产品 / 低碳产品 / 零碳产品"}}`。

### P2-5　设备读数没有删除接口（前端删除按钮 405）

**复现**：设备数据列表点"删除" → 后端无 `DELETE /api/device-readings/{id}`。

**实际**：405，前端提示失败；录错的读数只能改数值为 0，无法删除。

**修复**：新增 `ReadingService.delete` + `DELETE /api/device-readings/{id}`，删除前过 `PeriodGuard`（已定稿期间拒绝），写审计。

**验证**：删除返回 200，记录消失。

### P2-6　单元测试直接写演示库

**复现**：`mvn test` 后查库，`org`、`app_user`、`product` 数量增长。

**影响**：演示数据被测试反复污染；`SessionTenantTest` 会把主账号临时绑定到测试租户，若用例中途失败可能破坏演示账号；审计日志被测试操作填满（当前 4439 条）。

**根因**：`@SpringBootTest` 未指定 profile，直接使用 `application.yml` 中的演示库连接。

**修复**：
1. `ApiTestSupport` 增加 `@AfterAll` 租户清理（见 P1-3）；
2. `functional-cases.py` 增加 purge 调用；
3. 说明：理想方案是独立测试库，但当前数据库账号只有 `carbonbal` 库权限（`CREATE DATABASE` 被拒），已记录为遗留项。

### P3-1　单位产品能耗值允许负数（已修）

`l1/l2/l3` 传 `-1` 返回 200。生产报表会出现负能耗。已加 `@DecimalMin("0")`，返回 400。

### P3-2　碳资产年度无范围限制（已修）

`year=99999` 返回 200。已加 `@Min(2000) @Max(2100)`。

### P3-3　职责分离违规返回 409 而非 403（保留）

`SOD_VIOLATION` 映射到 409 `CONFLICT`。语义上更接近 403 `FORBIDDEN`（不是资源冲突，是角色约束）。改动会牵动 3 处测试断言与前端提示映射，收益低，本轮保留，建议下一轮统一。

## 五、通过项摘要（抽样）

**权限矩阵（70 次探测全绿）**

| 接口 | 匿名 | 业务成员 | 租户管理员 | 平台超管 |
|---|---|---|---|---|
| `GET /api/products` | 401 | 200 | 200 | 403 `PAGE_FORBIDDEN` |
| `GET /api/audit-logs` | 401 | 403 | 200 | 403 |
| `GET /api/users` | 401 | 403 | 200 | 403 |
| `GET /api/platform/overview` | 401 | 403 | 403 | 200 |
| `DELETE /api/products/{id}` | 401 | 403 | 200 | 403 |
| `GET /api/export` | 401 | 200 | 200 | 403 |

结论：平台侧与租户侧双向隔离正确；超管不能操作租户业务数据（无页面权限），符合设计。

**输入与协议（32 项全绿）**

- 空 body / 缺必填 / 类型错误 / 非法日期（2026-02-30、2026-13-01）→ 400 且带字段级提示
- 坏 JSON → 400；空 body → 400；`text/plain` → 415 `UNSUPPORTED_MEDIA_TYPE`
- 不存在 ID → 404 `NOT_FOUND`；非数字 ID → 400
- 分页 `size=0/100000/-1`、`page=0/-5` 全部钳制返回 200，不报错
- SQL 注入串按字面存储，未被解释；XSS 载荷落库后由前端 `esc` 转义
- 同编码重复创建 → 409 `DUPLICATE`；过期版本号更新 → 409 `VERSION_CONFLICT`

**状态机（18 项全绿）**

- 越级：`draft` 直接复核/批准/锁定/解锁 → 全部 400 且提示明确
- 重复提交 → 400；复核带过期版本 → 409
- 锁定后重算 → 409 `PERIOD_LOCKED`；解锁缺原因 → 400

**数据一致性（16 项全绿）**

产品/设备/读数/成员/角色/报告的外键引用 0 孤儿；唯一编码 0 重复；活跃租户均有有效许可证。

## 十、结论

系统核心业务链（读数 → 核算 → 审批 → 报告）在正常路径、越权路径、异常路径下的行为均符合预期；权限隔离与数据隔离经 70 次组合探测无越权；本轮修复的 3 个 P1 分别对应**信息泄露、审批链失真、演示数据污染**，都属于交付前必须解决的问题，现已全部验证通过。

剩余风险集中在"软删唯一键的剩余三处"与"测试库隔离"两项工程债，不影响功能正确性，建议在正式上线前处理。
