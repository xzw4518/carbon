## 一、方案

- **目标**：把原型「产值管理、碳核查支撑、能碳分析、报告查询、企业信息」对应的后端能力补齐，使 33 页不再出现「页面有、接口无」，并保持既有核算链路不回归。
- **旅程**：登记产值/凭证 → 设备读数与因子聚合出分析页 → 按类型生成报告 → 首页汇总 KPI/待办/预警 → 企业档案只读展示、管理员维护。
- **不做**：不改原型 33 页；不做 CSV/Excel 导出；不做定时预警扫描与报告自动生成；不做登录失败锁定、SSO、数据权限到人。

## 二、字段设计

| 字段 | 位置 | 必填 | 口径 / 枚举 | 真相源 |
|---|---|---|---|---|
| `period` | `production_value` / 月份 / 列表 | 是 | `YYYY-MM`，同月同产品唯一（`disabled=0`） | 服务层校验 |
| `product_id` / `product_name` | `production_value` | 是 | 引用 `product`；名称落库为快照 | `product` |
| `output_value` / `qty` | `production_value`、`total_value` | 是 | ≥0，4 位小数；产值单位与产量单位分列 | 表单 |
| `valid_from` / `valid_to` | `evidence`、`third_party_report` | 开始必填 | `DATE`；`valid_to < valid_from` → 400 | 表单 |
| `fileIds` | `evidence` | 否 | `null` 不动附件、`[]` 全部解绑 | `file_object` |
| `file_id` | `third_party_report` | 否 | 单文件；必须属于本企业且未删除 | `file_object` |
| `report_type` | `report` | 是 | `carbon / energy / footprint`，默认 carbon | 服务层 |
| `period_id` / `ref_id` | `report` | 否 | 碳/能源为核算期；足迹为 `product_footprint.id` | 业务表 |
| `short_name` … `license_file_id` | `org` | 名称/代码必填 | 工商档案；代码全局唯一 | `org` |

## 四、验收标准（AC）

1. `POST /api/production-values` 同月同产品第二次 → HTTP 409；`PATCH` 携带 `version=0` → 返回 `version=1`。
2. 核算期锁定后对同月产值 `POST` → HTTP 409，`message` 含「已锁定」。
3. 上传文件后创建凭证 → `files` 长度 1；`PATCH` 传 `fileIds: []` → `files` 长度 0；`validTo < validFrom` → 400。
4. `POST /api/reports {type:"energy",period:"2026-11"}` → 200，下载 `%PDF-`，`X-Content-SHA256` 与记录一致；`type:"footprint"` 缺 `footprintId` → 400。
5. 八个 `/api/analysis/*` 均返回 `kpis` 长度 4；`energy-flow` 的 `sankey.layers` 长度 3；`/api/overview` 的 `monthly` 长度 12。
6. `PATCH /api/org` 由 filler 调用 → 403；admin 用旧 `version` → 409。
7. 在 1 级设施下 `POST /api/facilities` → `level=2`；把 1 级设施挂到其子级 → 400；删除有下级的设施 → 409。
